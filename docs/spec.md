# Orbit 개인 비서 시스템 스펙

Nov 2, 2026 · @JIK

**Orbit** — **O**wn **R**untime, **B**ring-your-own **I**ntelligence **T**oolkit

*Your work, in your orbit.*

## 1. 개요

Orbit은 갤럭시 폰과 홈서버 맥(8GB)에서 돌아가는 오픈소스 개인 업무 비서다. 음성·알림·메일을 로컬에서 텍스트로 바꾸고, 일정과 할 일을 추출해 디스코드 승인을 거쳐 Google Calendar/Tasks에 등록한다.

### 1.1 목표

- 음성 메모 한 번으로 일정·할 일이 캘린더에 들어간다 (승인 1탭)
- 허용한 소스(Gmail, 지정 앱 알림, GitHub 등)에서 할 일을 놓치지 않는다
- 원본 데이터는 기본적으로 로컬(폰·홈서버)에 머문다
- 별도 UI 앱 없이 디스코드 서버 Orbit을 입력·승인·알림 창구로 쓴다

### 1.2 범위 (MVP)

- 안드로이드 수집 앱(Companion): 녹음 파일, 공유 인텐트, 지정 앱 알림
- 홈서버: 수집 API, STT, SLM 추출, 날짜 정규화, Google 연동
- 디스코드 봇 Orbit: 승인 버튼, 브리핑, 조회 명령

### 1.3 비목표

- 상시 녹음(통화·회의 자동 전체 녹음 트리거)
- 연구실 메신저(연구실 디스코드) 수집
- 승인 없는 완전 자동 쓰기 동작(등록·전송·공유)
- 플레이스토어 배포 (APK는 GitHub 릴리스로 배포)
- 채점 등 수업 운영 자동화

### 1.4 용어

| 용어 | 의미 |
| --- | --- |
| 이벤트 | 폰·소스에서 들어온 원시 입력 1건 (녹음, 알림, 메일 등) |
| 후보 | 이벤트에서 추출된 일정·할 일·마감 제안 1건 |
| 승인 | 디스코드에서 후보를 등록/수정/무시로 확정하는 행위 |
| 맥락 사전 | 사람·프로젝트·정기 일정 별칭을 정리한 YAML |
| 폴백 | 로컬 SLM 확신도가 낮을 때 상위 모델로 넘기는 경로 |

### 1.5 운영 원칙: 비용 0, BYO

Orbit 프로젝트는 서버를 운영하지 않는다. 중앙 백엔드, 계정, 결제가 없고, 모든 구성 요소는 사용자 본인의 기기와 본인의 키로 돈다. 프로젝트 측 운영비는 0이고, 사용자 비용은 본인 기기의 전기료와 (선택 시) 본인 API 사용량뿐이다.

- **컴퓨트 BYO**: 본인 PC, 노트북, 남는 맥, 미니PC 중 하나를 서버로 쓴다. 상시 켜둘 기기가 없으면 "지연 허용 모드"로 동작한다. PC가 켜져 있을 때만 처리하고, 그동안 폰 Companion 큐가 기다린다
- **LLM BYO**: 사용자가 추론 경로를 고른다

| 모드 | 사용자 비용 | 데이터 외부 전송 | 요구 사항 |
| --- | --- | --- | --- |
| 로컬 (llama.cpp·Ollama) | 0 | 없음 | RAM 8GB 이상 |
| CLI 구독 (Claude Code, Codex CLI 등) | 기존 구독 범위 | 해당 제공사 | 구독 계정 |
| 본인 API 키 (Anthropic, OpenAI, Google 등) | 사용량 과금 | 해당 제공사 | API 키, 월 상한 |
| 하이브리드 (기본 권장) | 0에 가까움 | 애매한 건만 | 로컬 + 위 중 하나 |

- **키 관리**: 키는 OS 키체인이나 암호화 파일에 저장한다. 월 예산 상한과 건당 토큰 상한을 두고, 상한에 닿으면 로컬로 강등하며 `#system`에 알린다
- **STT**: 로컬이 기본이다. API STT는 저사양 기기용 선택 옵션이다
- **외부 서비스는 무료 등급만 전제**: 디스코드, Google API 무료 할당량, Tailscale 개인 무료 플랜, GitHub 릴리스 배포. 유료 의존성은 추가하지 않는다는 규칙을 기여 가이드에 명시한다

## 2. 시스템 아키텍처

폰의 Companion이 Tailscale로 홈서버에 이벤트를 보내고, 홈서버가 판단과 외부 연동을 전부 맡는다. 디스코드는 수집 경로가 아니라 승인·알림 창구다.

> 그림: 시스템 구성 · 폰, 홈서버 4개 프로세스, 외부 서비스 (추가 예정)

Google 쓰기는 디스코드 승인을 거친 뒤 bot만 실행한다. 디스코드 `#inbox`로 들어온 수동 메모는 bot이 받아 같은 큐에 넣는다.

## 3. 안드로이드 수집 앱 (Companion)

Companion은 폰에서 이벤트를 모아 홈서버로 보내는 Kotlin 앱이다. 사이드로드로 설치하므로 스토어 정책상 막히는 권한(SMS, 전체 파일 접근)을 쓸 수 있다. 판단은 하지 않고 수집·필터·전송만 한다.

### 3.1 컴포넌트

| 컴포넌트 | 역할 | 권한 | 단계 |
| --- | --- | --- | --- |
| 공유 인텐트 대상 | 아무 앱에서 "공유 → Orbit"로 텍스트·링크·이미지·오디오 투척 | 없음 | M1 |
| `FileObserver` + `WorkManager` | 음성 녹음·통화 녹음 폴더 감시, 새 파일 업로드 | `MANAGE_EXTERNAL_STORAGE` | M2 |
| `NotificationListenerService` | 허용 목록 앱의 알림 수집 | 알림 접근 | M3 |
| SMS `BroadcastReceiver` | 문자 수집 | `RECEIVE_SMS` | M4 |
| 위치 트리거 | 지정 장소 도착·출발 이벤트 | 위치(백그라운드) | M4 |
| Room 큐 | 전송 실패분 저장, 재시도 | 없음 | M1 |
| 포그라운드 서비스 | 리스너·감시 상시 유지, 하트비트 송신 | 알림 표시 | M1 |

### 3.2 기기 단 필터 (서버 전송 전)

- 앱 허용 목록: 목록 밖 앱의 알림은 즉시 폐기
- 차단 정규식: 인증번호(`인증번호`, `[0-9]{4,8}` + 인증 키워드), 금융 거래 알림, 지정 키워드
- 알림 중복: 알림 `key` + 본문 해시로 동일 알림 업데이트를 1건으로 합침
- 녹음 파일: 확장자 화이트리스트(m4a, mp3, ogg, wav), 최소 길이 2초

### 3.3 전송

- 경로: Tailscale 망 안의 홈서버 `https://<tailnet-host>/ingest` (포트 외부 개방 없음)
- 인증: 기기별 Bearer 토큰. 서버에서 개별 폐기 가능
- 형식: JSON 이벤트(8장 스키마), 파일은 multipart. `captured_at`은 폰에서 캡처한 시각
- 재시도: 지수 백오프, Wi-Fi 전용 옵션(대용량 녹음)
- 하트비트: 15분 간격 `POST /heartbeat` (앱 버전, 리스너 상태, 큐 길이)

### 3.4 설치·운영 조건

- 배터리: 앱을 "제한 없음" + 절전 예외 앱에 등록. 미등록 시 One UI가 리스너를 종료한다
- 알림 접근 권한은 OS 업데이트 후 해제될 수 있음 → 하트비트에 리스너 상태 포함
- 앱 내 화면: 허용 목록 편집, 큐 상태, 마지막 전송 시각, 토큰 재발급 정도만

## 4. 홈서버

홈서버는 Apple Silicon 맥(8GB/512GB) 한 대에서 프로세스 4개로 돈다. 모델은 메모리 한계 때문에 상주시키지 않고 작업 단위로 순차 로딩한다.

### 4.1 프로세스

| 프로세스 | 기술 | 역할 |
| --- | --- | --- |
| `ingest` | FastAPI | 이벤트·파일 수신, 인증, 원본 저장, 큐 적재 |
| `worker` | Python, SQLite 큐 | STT → 분류 → 추출 → 정규화 → 후보 생성 |
| `watchers` | Python 스케줄러 | Gmail·GitHub·RSS 등 서버 측 소스 폴링 |
| `bot` | discord.py | 승인 UI, 브리핑, 명령, 장애 알림 |

모두 `launchd` 서비스로 등록하고 `KeepAlive`로 자동 재시작한다.

### 4.2 API

| 엔드포인트 | 설명 |
| --- | --- |
| `POST /ingest` | JSON 이벤트 수신 |
| `POST /ingest/file` | 녹음·첨부 파일 수신 (multipart) |
| `POST /heartbeat` | Companion 상태 보고 |
| `GET /health` | 서버 자가 점검 (큐 길이, 마지막 처리 시각, 디스크) |

### 4.3 자원 관리

- 메모리 예산: STT 모델 약 1.5GB, SLM(4B Q4) 약 3GB. 동시 로딩 금지, worker가 단계별로 로드·해제
- 처리 모드: 녹음은 즉시 처리, 알림·메일은 10분 배치
- 게임·코딩 등 포그라운드 사용 중에는 worker를 일시 정지하는 수동 토글(`/pause`) 제공
- 디스크: 원본 음성은 보존 기간(9장) 후 삭제, DB·로그는 주간 백업

### 4.4 디렉터리

```
orbit/
  data/raw/        # 원본 파일 (보존 기간 후 삭제)
  data/orbit.db   # SQLite
  config/context.yaml   # 맥락 사전
  config/sources.yaml   # 소스별 설정, 폴백 허용 여부
  secrets/         # 토큰 (키체인 참조)
  logs/
```

### 4.5 코어·워커 분리 (NAS 지원)

상시 동작과 무거운 추론을 분리한다. 코어는 24시간 켜진 저전력 기기에서, 추론은 힘 있는 기기나 API에서 돌린다. NAS는 코어로 가장 잘 맞는다.

| 역할 | 담당 프로세스 | 요구 사양 | 적합한 기기 |
| --- | --- | --- | --- |
| 코어 | ingest, bot, watchers, SQLite, 작업 큐 | RAM 1\~2GB, 상시 전원 | NAS, 미니PC, 남는 맥 |
| 워커 | STT, 분류·추출 (`worker`의 추론 부분) | RAM 8GB 이상 또는 GPU | PC, 맥, 고사양 NAS |
| 원격 워커 | 같은 작업을 본인 API 키로 처리 | 키 | 어디서나 |

- 워커는 Tailscale로 코어에 접속해 작업을 가져가는 pull 방식이다. 워커가 없으면 작업이 큐에 쌓이고, PC를 켜면 밀린 작업을 처리한다 (1.5 지연 허용 모드의 일반화)
- 코어와 워커가 한 기기여도 된다. 지금의 맥 단독 구성은 "코어 + 워커 동거" 프리셋이다
- 작업마다 허용 워커를 지정한다. 기밀 소스(`fallback_allowed = false`)는 원격 워커로 보내지 않는다
- NAS 배포: Docker Compose 이미지로 제공한다(amd64·arm64 멀티아키텍처). Synology Container Manager, QNAP Container Station, TrueNAS·Unraid 앱에서 동작하는 것을 목표로 한다
- NAS 제약: 키체인이 없으므로 비밀은 Docker secret이나 암호화 파일에 둔다. 저사양 NAS(ARM, RAM 2GB급)는 코어 전용으로만 지원하고, x86 + RAM 8GB 이상이면 소형 STT·추출 모델을 배치 처리로 돌릴 수 있다

### 4.6 공유 워커 (지인 간)

워커 하나를 지인 여러 명의 코어가 같이 쓸 수 있게 한다. 자기 PC가 없는 지인이 추가 비용 없이 로컬급 추출을 쓰기 위한 기능이다.

| 워커 신뢰 등급 | 예 | 데이터가 가는 곳 | 기본 허용 |
| --- | --- | --- | --- |
| local | 내 PC·맥 | 내 기기 | 모든 소스 |
| trusted | 지인이 공유한 워커 | 지인 기기 | 사용자 코어 설정에 따름 |
| remote | 본인 API 키 | 제공사 | 사용자가 소스별로 opt-in |

- **연결**: 워커 주인이 Tailscale 노드 공유로 워커만 지인 tailnet에 노출한다. 코어끼리는 서로 보이지 않는다
- **인증**: 지인 코어마다 워커 토큰을 발급하고 개별 폐기할 수 있다
- **무상태 처리**: 워커는 작업을 메모리에서 처리하고 결과만 돌려준다. 원본·결과를 디스크에 쓰지 않고, 로그에는 작업 ID·길이·처리 시간만 남긴다
- **최소 전송**: 코어가 가능한 전처리(텍스트 알림, 기기 단 필터)를 먼저 하고, 추출에 필요한 텍스트·음성만 보낸다
- **공정성**: 코어별 동시 작업 수와 일일 처리량 상한을 둔다. 주인의 작업이 항상 우선하고, 주인이 `/pause`하면 공유 작업도 멈춘다
- **설정 주체**: 어떤 소스를 공유 워커로 보낼지는 지인 본인의 코어 설정이 정한다. 워커 쪽은 별도 정책을 강제하지 않는다

## 5. 처리 파이프라인

모든 이벤트는 같은 6단계를 거친다. SLM은 구조화 추출만 맡고, 날짜 계산과 검증은 규칙 코드가 맡는다.

1. **텍스트화**: 음성은 whisper.cpp(large-v3-turbo급, Metal 가속)로 STT. 맥락 사전의 고유명사를 initial prompt로 주입한다. 알림·메일은 그대로 통과.
2. **분류**: SLM이 `schedule | task | deadline | note | ignore` 중 하나와 확신도(0\~1)를 낸다.
3. **추출**: 유형별 JSON 스키마로 출력을 강제한다(llama.cpp GBNF 또는 Ollama structured outputs). 날짜는 계산하지 않고 원문 표현만 뽑는다.
   - 예: `{"title": "교수님 면담", "date_expr": "다음 주 화요일", "time_expr": "오후 3시", "duration_expr": null, "people": ["교수님"], "project": null}`
4. **정규화**: 규칙 코드가 `captured_at`(캡처 시각) 기준으로 상대 표현을 절대 시각으로 바꾼다. 처리 시각 기준이 아니다.
   - 모호 표현 기본값: 점심 12:00, 오후(시각 없음) 14:00, 저녁 19:00, 기간 미지정 60분. 기본값을 쓴 필드는 `assumed`로 표시
   - 맥락 사전으로 별칭 해석: "교수님" → 실명, "그 과제" → 프로젝트명, "이번 주 미팅" → 정기 일정 인스턴스
5. **검증**: 과거 시각, 잘못된 날짜, 필수 필드 누락을 거른다. Calendar free/busy를 조회해 충돌을 표시하고, 이미 있는 후보·일정과 중복을 검사한다.
6. **후보 생성**: 후보를 DB에 저장하고 디스코드 승인 큐로 보낸다(6장).

### 5.1 분기 규칙

| 조건 | 처리 |
| --- | --- |
| 확신도 ≥ 0.8 | 승인 큐 (즉시 또는 브리핑, 6.3 기준) |
| 0.5 ≤ 확신도 < 0.8 | 폴백 허용 소스면 폴백 재추출, 아니면 "확인 필요" 표시 |
| 확신도 < 0.5 또는 `ignore` | 기록만 하고 일일 다이제스트에 집계 |
| `schedule` 인데 날짜 해석 실패 | `task`로 강등해 할 일로 제안 |

### 5.2 모델

| 용도 | 기본 | 비고 |
| --- | --- | --- |
| STT | whisper.cpp large-v3-turbo급 | 한국어, 영어 혼용 용어 사전 주입 |
| 분류·추출 | 3\~4B instruct, Q4 | 버전 고정, 교체 시 회귀 테스트(11장) |
| 임베딩 (M5) | 소형 다국어 임베딩 | 중복 판정, 과거 기록 검색 |
| 폴백 | 사용자 선택: CLI 구독 또는 본인 API 키 (1.5) | 소스별 허용 플래그, 월 호출 상한 |

## 6. 디스코드 인터페이스

디스코드 서버 Orbit의 Orbit 봇이 유일한 사용자 화면이다. 수집 데이터는 디스코드를 경유하지 않고, 후보·결과·알림만 올라간다. 일정·할 일의 원본은 Google Calendar/Tasks이고, 디스코드 채널은 그 뷰다.

### 6.1 Orbit 채널 구성

기존 Orbit(INBOX · RESEARCH · LIFE)을 유지하되, INBOX를 매일 보는 HQ로 바꾸고 비서 채널을 그 안에 모은다.

설계 원칙:

- **입력과 출력 분리**: 내가 쓰는 채널(inbox, drop, chat)과 봇이 쓰는 채널(today, approve, todo, system)을 섞지 않는다
- **봇 전용 채널은 쓰기 잠금**: @everyone의 메시지 보내기를 끄고 봇 역할만 허용한다. 잡담·오타가 섞이지 않는다
- **알림은 approve와 system만**: 나머지는 음소거하고 브리핑으로 본다 (6.3)
- **이름 규칙 유지**: 기존처럼 영문 소문자 한 단어
- **수정 대화는 스레드**: 후보 카드마다 스레드를 열어 채널 본문을 깨끗하게 둔다

| 카테고리 | 채널 | 쓰는 쪽 | 용도 | 변경 |
| --- | --- | --- | --- | --- |
| HQ | `#today` | 봇 | 아침·저녁 브리핑, 일일 다이제스트 | LIFE에서 이동 |
| HQ | `#inbox` | 나 | 텍스트·음성 메시지 메모 투척. 처리 후 원본 삭제 | `#log` 개명 |
| HQ | `#drop` | 나 | 파일 투척 (PDF, 녹음 파일 등) | 유지 |
| HQ | `#approve` | 봇 | 후보 카드 + 승인 버튼 | 신규 |
| HQ | `#todo` | 봇 | 확정 할 일 뷰, 완료 버튼 | 신규 |
| HQ | `#chat` | 나 ↔ 봇 | 대화형 질의·지시 | 유지 |
| RESEARCH | `#paper` | 나 | 논문 스크랩. 포럼 채널로 바꿔 논문별 게시글 + 태그(미읽음/요약됨/인용) | 포럼 전환 |
| RESEARCH | `#digest` | 봇 | 논문 다이제스트 | 유지 |
| RESEARCH | `#exp` | 나 | 실험 결과 정리 | 유지 |
| RESEARCH | `#report` | 봇 | 주간보고 초안 | 유지 |
| RESEARCH | `#due` | 봇 | 학회·투고 마감, 투고 상태 | 유지 |
| LIFE | `#workout` `#setlist` `#finance` | 나 | 기존 용도 | 유지 |
| SYSTEM (접힘) | `#system` | 봇 | 하트비트 끊김, 처리 실패, 토큰 만료 | 신규 |
| SYSTEM (접힘) | `#audit` | 봇 | 등록·수정·무시 기록 (원문 ↔ 결과) | 신규 |

작업 순서: INBOX → HQ 개명 · `#log` → `#inbox` 개명 · `#today`를 HQ 최상단으로 이동 · `#approve` `#todo` 생성 · SYSTEM 카테고리 생성 후 접기 · `#paper` 포럼 전환 · 봇 전용 채널 권한 설정.

위 구성은 대학원생 팩 기준이다. HQ와 SYSTEM은 모든 사용자에게 공통이고, RESEARCH·LIFE 같은 나머지 카테고리는 사용자가 고른 팩이 정한다 (16장).

### 6.2 후보 카드

- 표시: 유형, 제목, 일시(`assumed` 필드는 "추정" 표기), 대상 캘린더, 충돌 경고, 원문 발췌, 출처(녹음/알림/메일), 확신도
- 버튼: **등록** · **수정**(모달: 제목·일시·캘린더) · **할 일로** · **무시**
- 등록 후 카드에 Calendar 링크를 붙이고 버튼을 비활성화한다. 24시간 미처리 카드는 저녁 브리핑에 재노출

### 6.3 알림 등급

| 등급 | 조건 | 전달 |
| --- | --- | --- |
| 즉시 | 오늘·내일 일정, 48시간 내 마감 | `#approve` + 푸시 |
| 묶음 | 그 외 확신도 ≥ 0.8 | 아침(08:30)·저녁(21:00) 브리핑 |
| 조용히 | 확신도 낮음, `ignore` | 다이제스트 집계만 |

### 6.4 명령

| 명령 | 동작 |
| --- | --- |
| `/오늘`, `/내일`, `/이번주` | 일정·할 일 요약 |
| `/할일 [추가 내용]` | 할 일 조회 또는 직접 추가 |
| `/상태` | 서버·폰·소스별 마지막 처리 시각, 큐 길이 |
| `/pause`, `/resume` | worker 일시 정지·재개 |
| `/찾기 <질의>` (M5) | 과거 기록 검색 |

그 밖의 명령: `/undo <id>` (10.3), `/놓침` (11.1), `/사전` (8.3), `/bind`·`/unbind` (17.2).

### 6.5 일일 다이제스트

저녁 브리핑 끝에 "오늘 수집 N건 · 후보 M건 · 등록 K건 · 무시 J건 · 소스별 건수"를 붙인다. 평소보다 수집이 급감한 소스는 강조한다. 누락을 눈으로 확인하는 장치다.

## 7. 외부 연동

Google 연동은 OAuth 앱 하나로 묶고, 쓰기 스코프는 Calendar 이벤트와 Tasks로 한정한다. 서버 측 소스는 증분만 읽는다.

### 7.1 Google

| API | 스코프 | 용도 |
| --- | --- | --- |
| Calendar | `calendar.events`, `calendar.freebusy` | 후보 등록, 충돌 검사 |
| Tasks | `tasks` | 할 일 등록·완료 동기화 |
| Gmail | `gmail.readonly` | 할 일·일정 추출 (M3) |

- OAuth 앱은 "프로덕션" 상태로 둔다. "테스트" 상태면 refresh token이 7일 후 만료된다. 본인 전용이면 미검증 경고 화면을 거쳐 사용 가능하나, `gmail.readonly` 같은 제한 스코프 정책은 세팅 시 확인한다
- 캘린더 분리: 연구 · 수업 · 랩 운영 · 개인 + "Orbit 제안" 캘린더. 추출 단계에서 대상 캘린더도 분류한다
- Orbit이 만든 이벤트에는 `extendedProperties.private.orbit_id`를 넣어 추적·수정·롤백에 쓴다

### 7.2 서버 측 소스

| 소스 | 방식 | 주기 | 단계 |
| --- | --- | --- | --- |
| Gmail | History API 증분 조회 (`historyId` 저장) | 10분 | M3 |
| 학교 메일 (Gmail 아님) | IMAP `UID` 증분 | 10분 | M4 |
| GitHub | notifications API, 본인 저장소 이슈·PR | 30분 | M4 |
| 학회 CFP·공지 | RSS 또는 페이지 diff | 1일 | M4 |
| Google Drive | changes API | 1시간 | 미정 |

- 소스별 커서(마지막 ID·시각)는 `sources` 테이블에 저장해 재시작 후에도 이어 읽는다
- 소스별 `fallback_allowed` 플래그로 외부 모델 전송 여부를 통제한다 (9장)

### 7.3 PC 입력 (M4)

노트북에서 녹음한 회의 파일은 데스크톱 업로더(폴더 감시 스크립트)가 같은 `/ingest/file`로 보낸다. 폰 경로와 같은 파이프라인을 탄다.

## 8. 데이터 모델

저장소는 SQLite 하나다. 이벤트는 소스와 무관한 단일 스키마로 받고, 후보와 승인 결과를 원문에 연결해 감사와 평가에 같이 쓴다.

### 8.1 이벤트 스키마 (`/ingest`)

```json
{
  "event_id": "uuid",
  "source": "phone | gmail | github | rss | desktop | discord",
  "app": "com.kakao.talk",
  "type": "audio | notification | sms | share | email | location",
  "captured_at": "2026-11-02T15:24:00+09:00",
  "payload": { "title": "...", "text": "...", "file_ref": "raw/....m4a" },
  "dedupe_key": "sha256(...)",
  "device_id": "galaxy-01"
}
```

`captured_at`은 캡처 시각이며 날짜 정규화의 기준이다. 서버 수신 시각은 `received_at`으로 따로 둔다.

### 8.2 테이블

| 테이블 | 주요 컬럼 | 비고 |
| --- | --- | --- |
| `events` | event\_id, source, type, captured\_at, received\_at, text, file\_ref, dedupe\_key, status | status: queued / processed / failed |
| `candidates` | cand\_id, event\_id, kind, fields(JSON), assumed(JSON), confidence, model, calendar, conflict | kind: schedule / task / deadline / note |
| `decisions` | cand\_id, action, edited\_fields(JSON), decided\_at, google\_id | action: approve / edit / to\_task / ignore. 평가 데이터셋의 원천 |
| `sources` | source, cursor, last\_ok\_at, fallback\_allowed, retention\_days | 증분 커서와 정책 |
| `heartbeats` | device\_id, at, app\_version, listener\_ok, queue\_len | 장애 감지 |
| `embeddings` (M5) | event\_id, vector | 중복 판정, `/찾기` |

### 8.3 맥락 사전 (`config/context.yaml`)

```yaml
people:
  - name: <실명>
    aliases: [교수님, 지도교수님]
    role: advisor
projects:
  - name: <정식명>
    aliases: [그 과제, 논문 1]
    calendar: 연구
    deadline: 2026-12-31
recurring:
  - title: 랩 미팅
    rule: 매주 <요일> <시각>
    calendar: 랩 운영
defaults:
  lunch: "12:00"
  afternoon: "14:00"
  evening: "19:00"
  duration_min: 60
```

맥락 사전은 추출 프롬프트에 주입하고, 정규화 단계의 별칭 해석에도 쓴다. 디스코드 `/사전` 명령으로 항목을 추가할 수 있게 한다.

## 9. 보안·프라이버시·법적 고려

원칙은 세 가지다. 외부에서 들어온 텍스트는 데이터일 뿐 명령이 아니다. 쓰기 동작은 전부 사람 승인을 거친다. 민감한 데이터는 수집 단계에서 먼저 버린다.

### 9.1 프롬프트 인젝션

- 메일·알림 본문은 추출 프롬프트에 데이터 블록으로만 넣고, 시스템 지시와 분리한다
- SLM 출력은 스키마 필드로만 받는다. 출력에서 도구 호출이나 자유 지시를 해석하지 않는다
- 등록·전송·공유 등 모든 쓰기는 `#approve` 승인 후에만 실행한다. 봇은 메일 발송·파일 공유 권한을 갖지 않는다

### 9.2 권한·비밀

- Google 스코프 최소화 (7.1). 읽기 토큰과 쓰기 토큰 분리 저장
- 토큰은 macOS 키체인에 저장하고 코드·설정 파일에 두지 않는다
- Companion 토큰은 기기별 발급, 서버에서 개별 폐기
- 폰 분실 절차: Tailscale에서 기기 제거 → 기기 토큰 폐기 → Google 세션 점검. 절차를 `#system` 고정 메시지로 둔다

### 9.3 데이터 경계

| 데이터 | 처리 |
| --- | --- |
| 산학·특허 등 기밀 소스 | `fallback_allowed = false`. 로컬 SLM만 사용 |
| 학생 개인정보 (성적·연락처) | 수집 필터로 차단, 차단 실패 시 보존 7일 |
| 타인 메시지 (카톡 알림 등) | 허용 목록 앱만, 추출 후 원문 보존 30일 |
| 인증번호·금융 알림 | 기기 단에서 폐기, 서버 미전송 |
| 연구실 디스코드 | 수집하지 않음 |

### 9.4 보존 정책

| 대상 | 기본 보존 |
| --- | --- |
| 원본 음성 | STT 후 14일 |
| 이벤트 원문 | 90일 (소스별 `retention_days`로 조정) |
| 후보·승인 기록 | 영구 (평가 데이터셋) |
| 로그 | 30일 |

### 9.5 법적 고려

- 본인이 참여한 대화 녹음은 통신비밀보호법상 허용된다. 본인이 빠진 대화 녹음은 금지된다
- 면담·랩 미팅 녹음은 사전 고지를 원칙으로 한다
- 학생 정보는 개인정보보호법 대상이므로 수집 최소화가 기본이다
- 회의록 등 타인에게 공개되는 출력은 반드시 사람 검수 후 게시한다

## 10. 신뢰성·운영

업무용에서 가장 위험한 실패는 조용한 누락이다. 모든 구성 요소가 살아 있음을 스스로 보고하고, 끊기면 `#system`에 알린다.

### 10.1 장애 감지

| 대상 | 감지 | 알림 조건 |
| --- | --- | --- |
| Companion | 하트비트 | 60분 무신호, `listener_ok = false` |
| 서버 프로세스 | `launchd` KeepAlive + `/health` | 재시작 3회/시간 초과 |
| 소스 커서 | `sources.last_ok_at` | 소스별 주기 × 3 경과 |
| Google 토큰 | API 401 | 즉시 |
| 큐 | 큐 길이 | 50건 초과 또는 1시간 이상 정체 |
| 디스크 | 여유 공간 | 20GB 미만 |

### 10.2 전원·부팅

- 정전 후 자동 부팅(에너지 설정의 "정전 후 자동 시작")과 자동 로그인을 켠다
- FileVault와 충돌: FileVault를 켜면 정전 후 재부팅 시 로그인 화면에서 멈춘다. 계획된 재시작은 `fdesetup authrestart`로 넘길 수 있으나 정전은 막을 수 없다. 결정: FileVault는 끈다. 토큰은 키체인에 두고, DB·원본 음성 등 민감 데이터는 앱 수준 암호화(SQLCipher 등)로 보호한다
- 잠자기 방지: 디스플레이만 끄고 시스템 잠자기는 끈다

### 10.3 감사·롤백

- 모든 등록·수정·무시는 `#audit`와 `decisions` 테이블에 원문 ↔ 결과로 남긴다
- Orbit이 만든 Google 이벤트는 `orbit_id`로 식별해 `/undo <id>`로 되돌린다

### 10.4 백업·업데이트

- 매일 03:00 SQLite 온라인 백업, `config/` 포함. 주 1회 외장 디스크 또는 클라우드로 복사 (암호화)
- 모델·의존성 버전 고정. 교체 시 회귀 테스트 통과 후 반영 (11장)
- 안드로이드 메이저 업데이트, 디스코드·Google API 변경은 연 수회 깨진다고 가정하고 하트비트·토큰 알림으로 감지한다

### 10.5 대체 경로

Orbit은 보조 수단이다. 서버가 죽어도 캘린더·할 일 앱을 직접 쓰는 기존 습관을 유지한다.

## 11. 평가·개선 루프

승인 버튼의 결과가 곧 정답 라벨이다. 별도 라벨링 없이 `decisions` 테이블이 평가 데이터셋으로 쌓인다.

### 11.1 지표 (주간, `#report`에 자동 게시)

| 지표 | 정의 | 목표 (M2 종료 시) |
| --- | --- | --- |
| 승인율 | approve / 전체 후보 | ≥ 70% |
| 무수정 승인율 | 수정 없이 approve / 전체 후보 | ≥ 50% |
| 일시 정확도 | 수정 전후 일시 일치 비율 | ≥ 85% |
| 누락 신고 | 직접 등록했는데 Orbit이 못 잡은 건 (`/놓침` 명령) | 추세 감소 |
| 폴백 비율 | 폴백 호출 / 전체 추출 | ≤ 20% |
| 처리 지연 | 캡처 → 후보 게시 중앙값 | 녹음 ≤ 2분 |

목표 수치는 초기 가정이다. 2주 사용 후 실측으로 재설정한다.

### 11.2 개선 절차

1. 주간 리포트에서 수정·무시가 많은 패턴을 뽑는다 (날짜 표현, 특정 소스, 특정 사람 호칭)
2. 맥락 사전 보강 → 프롬프트 수정 → 규칙 추가 순으로 싼 것부터 고친다
3. 변경 전후를 고정 회귀 세트(최근 승인 기록 200건)로 비교하고, 나빠지지 않을 때만 반영한다
4. 데이터가 1,000건 이상 쌓이면 LoRA 경량 파인튜닝을 검토한다

### 11.3 가치 측정

기능 추가 기준은 "주당 몇 분을 아껴주는가"다. 월 1회 실제 사용 빈도가 낮은 기능은 끄거나 제거한다.

## 15. 오픈소스 배포와 원큐 설치

`orbit init` 한 번으로 서버 설치부터 디스코드 서버 구성까지 끝내는 것을 목표로 한다. 외부 서비스가 사람 확인을 요구하는 단계는 자동화할 수 없으므로, 마법사가 그 단계에서 링크를 띄우고 입력을 기다린다.

### 15.1 자동화 범위

| 단계 | 자동화 | 방식 |
| --- | --- | --- |
| 디스코드 앱·봇 토큰 발급 | 수동 | Developer Portal에서 생성 후 토큰 붙여넣기. 앱 생성 API는 없다 |
| 디스코드 서버 준비 | 수동 | 빈 서버를 만들거나 기존 서버 사용 |
| 봇 초대 | 반자동 | 필요 권한이 포함된 초대 URL 생성, 클릭 1회 |
| 카테고리·채널·권한·포럼 태그·고정 메시지 | 자동 | `orbit.discord.yaml` 선언 → 봇이 API로 생성 (15.2) |
| Google OAuth 클라이언트 | 수동 | 사용자 본인 Cloud 프로젝트에 생성 후 JSON 지정 |
| Google 계정 연결 | 반자동 | 로컬 브라우저 OAuth, 토큰은 키체인 저장 |
| Tailscale | 반자동 | 설치 후 로그인 1회 |
| 모델 다운로드 | 자동 | RAM 감지 → 프리셋 선택 (8GB: STT turbo + 4B Q4) |
| 서비스 등록 | 자동 | macOS `launchd`, Linux `systemd`, NAS·Windows는 Docker Compose |
| Companion 연결 | 반자동 | APK 설치·권한 허용 후 서버가 띄운 QR로 주소·기기 토큰 페어링 |

Google OAuth는 사용자별 클라이언트(BYO) 방식이다. 공용 클라이언트를 배포하면 Gmail 제한 스코프 때문에 Google 검증이 필요해진다.

### 15.2 디스코드 선언형 구성

```yaml
# orbit.discord.yaml
categories:
  - name: HQ
    channels:
      - { name: today,   writer: bot }
      - { name: inbox,   writer: me, rename_from: log }
      - { name: drop,    writer: me }
      - { name: approve, writer: bot, notify: all }
      - { name: todo,    writer: bot }
      - { name: chat,    writer: both }
  - name: RESEARCH
    channels:
      - { name: paper, type: forum, tags: [미읽음, 요약됨, 인용] }
      - { name: digest, writer: bot }
  - name: SYSTEM
    collapsed: true
    channels:
      - { name: system, writer: bot, notify: all }
      - { name: audit,  writer: bot }
```

- `orbit discord apply`: 현재 서버와 비교한 diff를 보여준 뒤 적용한다. 이름·`rename_from`으로 매칭해 기존 채널은 개명·이동하고, 삭제는 `--prune`을 줄 때만 한다. 여러 번 실행해도 결과가 같다(멱등)
- `orbit discord export`: 기존 서버 구성을 YAML로 뽑는다. 현재 Orbit 서버를 기준 템플릿으로 삼을 수 있다
- 봇 권한: 채널 관리, 역할 관리(채널 권한 설정용), 메시지 보내기·관리(inbox 원본 삭제), 스레드 생성, 메시지 기록 읽기. 관리자 권한은 요구하지 않는다
- 채널 이름은 설정값으로 두고, 코드는 채널 역할 키(`approve`, `system` 등)로만 참조한다

### 15.3 원큐 흐름

1. `git clone` 후 `./install.sh`: 런타임·의존성 설치, `orbit` CLI 등록
2. `orbit init` 마법사: 봇 토큰 입력 → 초대 링크 클릭 → 디스코드 apply → Google 연결 → 모델 다운로드 → 서비스 등록 → QR 페어링
3. `orbit doctor`: 토큰·권한·채널·모델·하트비트를 점검하고 실패 항목과 해결 방법을 출력

### 15.4 오픈소스 설계 원칙

- 개인 정보는 저장소에 두지 않는다: `context.yaml`, `sources.yaml`은 `*.example`만 커밋하고 실제 파일은 `.gitignore`
- 텔레메트리 없음
- 어댑터 구조: 메신저(디스코드 기본), 캘린더·할 일, LLM 런타임(llama.cpp·Ollama·CLI 폴백)을 인터페이스로 분리해 교체 가능하게 한다
- 로케일 분리: 한국어 날짜·시간 표현 규칙은 `locale/ko` 모듈로 두고 다른 언어를 추가할 수 있게 한다
- 플랫폼: macOS·Linux 우선, NAS는 Docker로 코어 지원(4.5). 본인 PC가 Windows인 사용자가 많으므로 Windows는 WSL2 또는 Docker로 지원한다
- 저장소: `server/` · `companion/`(안드로이드) · `deploy/`(install, launchd·systemd) · `docs/`
- 일정: M1\~M2는 본인 세팅을 스크립트로만 남기고, 원큐 설치와 공개 저장소 정리는 M3 이후에 한다. 라이선스(MIT 또는 Apache-2.0)는 공개 전에 정한다

## 16. 사용자 유형 확장 (팩)

코어는 직군을 모른다. 직군별 차이는 **팩**이 담당한다. 팩은 채널 구성, 소스 어댑터, 추가 추출 유형, 맥락 사전 템플릿, 브리핑 규칙을 묶은 설정 묶음이다. 여러 팩을 겹쳐 쓸 수 있고, 업무가 바뀌면 팩을 바꾼다.

### 16.1 코어와 팩의 경계

| 계층 | 담는 것 | 직군 의존 |
| --- | --- | --- |
| 코어 | 수집 API, STT, 분류·추출 엔진, 정규화, 승인 흐름, 감사, 평가 | 없음 |
| base 팩 | HQ(today·inbox·drop·approve·todo·chat), SYSTEM 채널 | 없음 (항상 설치) |
| 직군 팩 | 추가 채널, 추가 유형·스키마, 활성 소스, 맥락 사전 템플릿, 브리핑 항목, few-shot 예시 | 있음 |
| 로케일 | 날짜·시간·교대 표현 규칙 | 언어별 |

### 16.2 팩 정의

```yaml
# packs/lecturer/pack.yaml
name: lecturer
extends: [base]
kinds:                       # 코어 유형에 매핑되는 하위 유형만 추가
  - { id: assignment,      base: deadline, fields: [course, due] }
  - { id: student_request, base: task,     fields: [student_ref, course] }
sources: [gmail, lms_rss]
filters: [student_pii]       # 기본 ON 필터
channels: discord.yaml
context_template: context.example.yaml
briefing:
  morning: [today_classes, due_48h]
fewshot: examples.jsonl
```

추가 유형은 반드시 코어 유형(schedule·task·deadline·note) 중 하나로 매핑한다. 그래야 캘린더·할 일 등록, 승인, 평가 로직을 코어가 그대로 처리한다.

### 16.3 직군별 팩 초안

| 팩 | 주요 입력 | 추가 유형 | 채널 예 | 특이 요구 |
| --- | --- | --- | --- | --- |
| 대학원생 | 녹음, Gmail, GitHub, CFP | 투고 마감, 미팅 액션 아이템 | paper, exp, digest, report, due | 주간보고 생성 |
| 강의자 | 메일, LMS 공지, 학생 문의 알림 | 과제 마감, 학생 요청, 수업 변경 | class, assign, ask | 학생 개인정보 필터 기본 ON |
| 엔지니어 | GitHub·Jira, 업무 메신저 알림, 회의 녹음 | 리뷰 요청, 온콜, 배포 일정 | review, oncall, meeting | 이슈 트래커 어댑터 |
| 현장노동자 | 음성 메시지, 문자(근무표·작업 지시), 사진 | 교대 근무, 작업 지시, 안전교육, 연장근무 기록 | shift, order, worklog | 핸즈프리·소음·오프라인, 쉬운 설치 (16.4) |

### 16.4 현장노동자 팩의 별도 요구

네 유형 중 가장 다르다. 책상·PC를 전제한 설계가 그대로 통하지 않는다.

- **입력**: 장갑·소음 환경을 가정한다. 홈 화면 위젯이나 길게 누르기 한 번으로 녹음하고, STT 전에 음성 구간 검출(VAD)과 노이즈 제거를 넣는다. 근무표·작업지시서 사진은 OCR로 받는다
- **출력**: 버튼 수를 최소화하고, 후보를 음성으로 읽어주는(TTS) 확인 옵션을 둔다
- **연결**: 현장 통신이 불안정하다는 전제로 Companion 큐 보존 기간과 용량을 늘린다
- **교대 근무**: "주주야야비비" 같은 순환 패턴을 맥락 사전 `recurring`에서 지원해 "다음 야간 근무"를 해석한다
- **인프라**: 상시 켜둘 서버가 없을 수 있다. 집에 있는 아무 PC나 지연 허용 모드(1.5)로 쓰게 하고, 저사양 기기에는 "STT·추출 모두 본인 API 키" 프리셋을 둔다. 유료 클라우드 호스팅은 비용 0 원칙에 어긋나므로 기본 경로에 넣지 않는다
- **메신저**: 디스코드가 낯설 수 있다. 메신저 어댑터로 텔레그램 등을 대안으로 둔다. 카카오톡은 개인용 봇 연동 경로가 제한적이라 별도 검토가 필요하다

### 16.5 팩 선택과 전환

- `orbit init`에서 직군을 묻고 base + 직군 팩을 설치한다
- 겸업(예: 대학원생 + 강의자)은 팩 합성으로 푼다. 채널은 카테고리 단위로 병합, 유형·소스는 합집합, 이름이 충돌하면 팩 접두어를 붙인다
- 업무가 바뀌면 `orbit pack add/remove`로 바꾼다. 데이터는 유지하고, 빠진 팩의 채널은 삭제하지 않고 보관(archive) 카테고리로 옮긴다
- 팩의 few-shot은 시작점일 뿐이다. 승인 기록이 쌓이면 사용자 본인의 예시가 우선한다
- 팩은 커뮤니티 기여 단위로 둔다. 새 직군은 코어 수정 없이 `packs/<name>/`만 추가해서 지원한다

## 17. 채널 확장과 일상 위임

채널과 카테고리는 계속 늘어난다고 전제한다. 봇은 채널을 이름이 아니라 ID와 **동작 템플릿**으로 다루고, 사용자가 디스코드에서 직접 만든 채널도 명령 하나로 Orbit 기능에 연결한다. 일상 영역도 같은 방식으로 원하는 만큼만 맡긴다.

### 17.1 채널 소유 구분

| 구분 | 만드는 쪽 | Orbit 동작 | `orbit discord apply` 시 |
| --- | --- | --- | --- |
| managed | 팩·YAML | 팩이 정한 역할 | 생성·개명·이동 |
| bound | 사용자가 디스코드에서 만든 뒤 `/bind` | 고른 템플릿 | 연결 정보만 YAML로 역반영, 구조는 건드리지 않음 |
| unmanaged | 사용자 | 읽지 않음 | 무시 |

- 채널은 ID로 참조한다. 디스코드에서 이름을 바꾸거나 다른 카테고리로 옮겨도 연결이 유지된다
- `orbit discord export`는 현재 서버 상태(새 카테고리·채널 포함)를 YAML로 역반영한다. 설정 파일과 실제 서버가 어긋나지 않는다
- `--prune`은 managed 채널에만 적용된다. 사용자가 만든 채널은 어떤 명령으로도 자동 삭제되지 않는다
- 봇은 managed·bound 채널만 읽는다. 새 채널을 만들었다고 자동으로 수집하지 않는다 (9.3과 같은 원칙)

### 17.2 동작 템플릿

코드 없이 아무 채널에나 붙일 수 있는 범용 기능이다.

| 템플릿 | 하는 일 | 예 |
| --- | --- | --- |
| `inbox` | 메시지를 파이프라인에 투입해 일정·할 일 후보 생성 | #inbox, #idea |
| `log` | 자유 기록 저장, 주간 요약, 검색 대상 (M5) | #exp, #diary |
| `list` | 항목 추가·체크·삭제, 고정 메시지로 현재 목록 유지 | #setlist, #grocery, #wishlist |
| `tracker` | 숫자·반복 기록, 주간·월간 통계 | #workout, #finance |
| `feed` | 외부 소스 요약 게시 | #digest, #news |
| `reminder` | 반복 알림 | #plants, #bills |

- 명령: `/bind #채널 <템플릿> [옵션]`, `/unbind #채널`. 예: `/bind #grocery list`, `/bind #workout tracker unit=kg`
- 템플릿으로 표현되지 않는 기능은 팩(코드)으로 승격한다

### 17.3 일상 위임 (life 팩)

- 대상 예: 지인·가족 약속, 장보기·가사, 운동, 노래 목록, 지출 기록, 공과금·구독 납부일, 기념일
- 업무와 같은 파이프라인을 탄다. 분류 단계에서 업무/일상 영역을 함께 판정해 개인 캘린더와 LIFE 카테고리로 보낸다
- 기본은 OFF이고 영역별로 opt-in 한다. 소스·채널 단위로 켜고 끈다
- 경계 유지: 브리핑에서 업무와 일상 섹션을 분리하고, 조용한 시간(예: 23:00\~07:00)에는 즉시 알림을 보내지 않는다
- 지출 금액 등 민감한 일상 기록은 폴백 금지가 기본이고 보존 정책을 따로 둔다
